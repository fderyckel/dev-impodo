# Support data managers through the six-stage Authoring workflow

## Status and decision

**Status:** Ranked first in the cross-plan implementation order and reassessed
against the current checkout on 2026-10-29. Proposals 1, 2, 3, 4, 5, 6, 7, 8,
and 10 now have useful implemented foundations, while Proposal 9 is complete.
The shared root-cause correction journey from Proposals 1 and 8 now covers
Stage 2, current Stage 3 identity and relationship findings, complete-run
preparation causes in Stages 4 and 5, and Final-review-only blockers. Current
Stage 3 counts also remain visible in workspace navigation without opening a
second issue store. The exact prepared-value precision pass is implemented as
bounded, value-free worker evidence, and cause-specific drill-down uses
publication-time membership and readiness projections. The bounded Stage 3
check now also proves governed Many2one components in a dataset's own identity,
including recursively nested governed Many2one key components.
An authorized, freshness-checked page exposes only the bounded protected
unresolved choices for that current check. Source-backed Many2one relationship
health now uses the same recursive key tree. The next delivery should complete
the source-aware supporting-data closure from Proposal 2, followed by the
migration-intent part of Proposal 10. Do not build parallel
replacements for the implemented default, mapping-impact, comparison, or
load-recovery flows.

The current supported product remains the local application. The shared-server
track has completed its contract and composition phases and has started a
local PostgreSQL persistence trial, but no remote Impodo server is allocated
or qualified. This workflow plan therefore defines deployment-neutral product
behavior. It neither waits for the server release nor treats local DuckDB
access, process-local jobs, or the implicit local operator as shared product
contracts.

This plan is for the product owner and the developers who own Impodo's
six-stage Authoring workflow. It proposes how Impodo should help a data manager
make difficult migration decisions earlier, understand why work needs
attention, and return directly to the decision that must change.

The decision is to improve both the process and the browser together. A new
check without a clear correction route leaves the data manager blocked. A new
screen without authoritative evidence can create false confidence. Each
proposal therefore pairs one process change with one interface change.

### Implemented first slice

Stage 2 now derives direct supporting-model dependencies from live captured
Odoo fields and shows **Supporting data Impodo found**. It separates reuse of
existing records, checked defaults, Odoo-managed fields, and related incoming
business data without silently widening the write scope. A user can open the
record-type choices with an incoming model preselected, but must still save
that scope explicitly.

The slice also introduces a shared read-only workflow-issue projection. Stage
2 uses it when a related model is unavailable: the browser states the cause,
owner, affected fields, preserved work, correction route, and recheck. A
required unavailable reuse dependency blocks matching-rule confirmation in
both the interface and application service.

### Implemented second slice

Stage 3 now reuses its explicit bounded Odoo table-order check to prove saved
direct identities against current included source rows and records visible to
the current read user. **Identity health** separates **Suggested**, **Chosen -
not tested**, **Tested on current data**, **Tested - needs attention**, and
**Needs refresh**. It reports aggregate blank, repeated, exact, ambiguous, new,
existing, and blocked counts without publishing key values or numeric Odoo
IDs.

This slice deliberately does not weaken a relational identity into an
unscoped scalar check. A parent-, company-, or other related-record component
remains explicitly not tested. The first Proposal 6 slice checks saved
relationship fields but does not yet complete a dataset's resolver-backed
identity. Final review remains authoritative.

The shared issue projection now also presents complete-run preparation causes
on Stages 4 and 5. It sorts root findings before inherited dependencies, shows
the complete affected-record count and authoritative owner/policy, and opens
the closest saved Match-data field, relationship, Odoo-match, or data-check
decision without mutating it. The existing bounded quality-page read supplies
the projection; the browser adds no DuckDB open or Odoo call.

The remaining work does not yet pair file-source dependencies with accepted or
derived source tables, derive Recipe closure, authorize supporting reads,
include optional many-to-one or many-to-many fields from source or Recipe
intent, or prove relational identity components. The current Odoo-source
relationship scope, direct relationship health, and persistent Stage 3 issue
counts now cover parts of the earlier gap. A combined all-stage issue drawer
remains optional consolidation.

### Implemented third slice

Stage 3 now adds **Relationship health** to the same explicit bounded check.
For saved Many2one and Many2many fields with direct scalar related keys, it
checks target-only, incoming-only, and target-first providers against the
included owner rows and included related rows. It reports aggregate existing
Odoo, incoming, missing, ambiguous, case-only, incomplete compound-key, and
blank counts. A required blank blocks readiness; an optional blank does not.

The read planner groups distinct keys by related model and matching rule,
chunks them through the existing read-only path, and never makes a request per
source row. Dataset-only relationships do not read related Odoo records. Exact
keys and numeric Odoo IDs remain protected; the browser and portable Recipe
receive only counts and correction routes.

The slice also points an invalid One2many choice to the child dataset's inverse
Many2one when that selected route exists. It does not yet publish a protected
unresolved-value review page, simulate a relationship whose governed key
contains another related field, or complete resolver-backed dataset identity.

### Implemented fourth slice

After approved preparation, Stage 4 now exposes the same **Compare with Odoo**
action owned by Final review. Both entry points use one comparison job and one
saved result. Stage 4 does not introduce another target-reference checker or
Odoo scan.

For file-source comparisons with isolatable blockers, Stage 5 now offers
**Preview affected groups** and a reviewed **Set aside affected groups for this
load** decision. Dependency closure keeps required parents, children, and
siblings together; the reduced execution snapshot is rebuilt locally and the
workbook retains every omitted record with its direct or inherited reason.
Exact numeric-precision findings are evaluated against intended writes. The
preview, acceptance, and workbook do not contact Odoo, and stale comparison or
preview evidence is rejected.

### Implemented fifth slice

Final review now publishes a complete-run, value-free aggregate for every
blocking decision cause and ambiguous target match while the complete result
is already in memory. Records with several blocking causes contribute to every
relevant cause. Odoo-source refresh blockers use the same projection from
their already-built comparison rows.

The Final review page merges these counts into the shared **Migration issues**
journey. Each card shows the cause, owner, affected record type and count,
preserved work, and required recheck outside the paged row table. Its action
filters the existing bounded decision-page query by stable issue code. The
browser adds no database open, target scan, per-row call, or second issue
store. Older saved comparisons retain an actionable dataset-level fallback
until the next comparison publishes cause-specific counts.

### Implemented sixth slice

Current Stage 3 identity and relationship evidence now uses the same
**Migration issues** projection as the other implemented stages. Checked
blockers become **Must fix** cards; aggregate not-checkable results become
**Review** cards. Each card identifies the cause, correction owner, affected
record type and field, preserved work, exact Match-data anchor, and required
**Check current data** rerun. Invalid One2many choices retain the existing
child-inverse correction route.

The workspace sidebar persists the current Stage 3 **Must fix** and **Review**
counts on later pages. Its local repository reads only the current
aggregate-only `MatchingOrderCheck` after scalar source, schema, governance,
working-draft, target, principal, permission, and context bindings match. A
stale check contributes no navigation count. The read remains inside the
existing single navigation connection and transaction; it makes no Odoo call
and does not decode protected key values. A future shared-server adapter may
carry the same two counts and verified evidence pointer in PostgreSQL, but a
server page must not open worker-held DuckDB evidence.

### Implemented seventh slice

The explicit Stage 3 live check now proves a dataset identity whose key or
scope contains one governed Many2one component. The planner reads the complete
owner key through a dotted related-business-key domain, reads the related
records by their confirmed key and scope, and compares the owner identity in
memory with a protected symbolic related key. Target-only, incoming-only, and
target-first resolver origins retain their existing meaning. Numeric Odoo IDs
remain confined to the protected target snapshot and never become portable
identity evidence.

Related reads remain grouped by model, governed rule, scope, and distinct key.
The source side now reuses a broader row-aligned dataset projection when a
later identity or relationship probe needs only a subset of its columns. This
avoids an extra DuckDB scan in the common identity-plus-relationship path and
does not introduce a process-wide connection cache.

Missing or ambiguous related identity choices make the aggregate identity
explicitly not checkable. Their values and cause-specific match counts are
stored only in the protected check snapshot; ordinary cards, navigation, and
shared-server-safe projections still expose counts and correction routes only.
The next slice below adds the authorized paged review of those protected
choices. A related business key that itself contains another relation,
protected duplicate-group review, and target-wide blank inventory remain
planned.

### Implemented eighth slice

Stage 3 now provides **Review unresolved identity choices** when one governed
Many2one component cannot be proved uniquely. Check publication validates and
normalizes the protected choice rows in the same transaction as the protected
snapshot and current-check pointer. The page shows at most 100 rows, supports
allowlisted table, owner-field, and cause filters, and links each row back to
the exact matching rule. It never publishes numeric Odoo IDs.

The application query requires `PROTECTED_EVIDENCE_READ` and rechecks the
source, schema, governance, draft, target, credential, principal, permission,
and context bindings before it reads a page. Paging uses the normalized index;
it does not decode the complete protected snapshot or contact Odoo. The route
runs inside one bounded page-read operation and keeps ordinary identity cards,
workspace navigation, and shared-server-safe projections value-free.

This is a deployment-neutral use case rather than permission for a Linux web
process to open worker DuckDB state. The local adapter owns the current DuckDB
projection. A future shared-server adapter must publish and page an equivalent
bounded protected projection only after verifying the worker receipt. Nested
related identity keys were the next slice recorded below; duplicate-group
review and target-wide blank inventory remain planned.

### Implemented ninth slice

The Stage 3 identity probe now follows a governed Many2one business key whose
own key or scope contains another governed Many2one. It builds a depth-limited
tree from the saved dataset identity components, flattens only scalar leaves
for bounded Odoo domains, and resolves target relation IDs bottom-up in memory.
The complete nested token then enters the existing owner-identity classifier;
no display name or numeric Odoo ID becomes portable evidence.

Metadata and record requirements remain merged by model and field in the one
immutable check plan. Distinct leaf keys are deduplicated and chunked outside
source-row loops, while the row-aligned source projection cache reuses broader
dataset reads. Five related-key levels and 50,000 distinct values per node are
hard limits. A cycle, ambiguous saved shape, deeper chain, or unsupported field
stops before source or Odoo reads and remains explicitly not checkable.

Nested leaf failures reuse the existing protected choice projection. The page
shows the deepest dotted owner-field path and leaf business-key fields, while
ordinary cards, navigation, and shared-server-safe projections remain
value-free. The local DuckDB ownership and Linux worker-receipt boundary are
unchanged. Saved relationship-field health still supports direct scalar
related keys; the tenth slice below extends that simulator to the nested tree.

### Implemented tenth slice

Source-backed Many2one relationship health now reuses the recursive key tree
from the ninth slice. The prepared check normalizes the complete leaf key once,
resolves nested target records bottom-up, and passes protected portable tokens
to the existing aggregate classifier. Target-only, incoming-only, and
target-first origins retain their precedence, including nested case-only,
missing, and ambiguous outcomes.

The immutable requirement plan merges identity and relationship metadata by
model, deduplicates scalar leaf keys, and chunks them outside row loops. The
row-aligned source cache reuses a broader identity projection when the
relationship needs the same or fewer columns. A 1,000-row focused fixture uses
three source projections and fewer than 30 bounded Odoo record requests. A
cycle stops before either source or Odoo evidence is read.

Public relationship health remains aggregate-only. Protected keys stay in the
existing worker evidence, and this slice adds no browser route, DuckDB
repository, shared-server projection, or permission for a Linux web process to
open worker-held evidence. Nested Many2many and constant-provider keys remain
explicitly outside this Many2one slice.

## User goal

A data manager should be able to answer six questions before Impodo writes to
Odoo:

1. Did I accept the correct business records, and has Impodo identified the
   supporting Odoo data that those records need?
2. Can Impodo identify one intended Odoo record without using a numeric Odoo
   database ID?
3. Will every child record find exactly one intended parent, and will every
   other populated relationship resolve to exactly one intended record?
4. Does every required field have an explicit source value, approved constant,
   checked Odoo default, or Odoo-managed reason, and can Odoo store every
   prepared number without losing decimal precision?
5. Does the proposed result match the business purpose of this migration?
6. If work stops or needs correction, what is the one safe next action?

For the data manager, this means that Impodo should find identity,
relationship, and required-value risks as soon as enough evidence exists. It
must still repeat the authoritative checks against current prepared data and
fresh Odoo evidence before loading.

## Priority frustrations this plan must resolve

Four recurring failures should determine the first delivery slices and their
acceptance criteria.

### Technical Odoo dependencies must be Impodo's responsibility

In Stage 2, the data manager should choose the business records they intend to
migrate, such as Products or Bills of Materials. They should not need to know
in advance that the current Odoo configuration may also require Product
Categories, Units of Measure, Companies, Products used by Bills of Materials,
or another installed application's related record type.

Impodo should derive that dependency plan from the accepted source structure,
the selected top-level business records, the current captured Odoo schema, and
any applied Recipe. It should classify each related model as:

- incoming business data that the migration intends to create or update;
- an existing Odoo reference that Impodo reads only for matching;
- an Odoo-managed or checked-default dependency that needs no incoming data;
  or
- an unresolved business decision that prevents the workflow from advancing.

The normal path should ask only the remaining business question, such as
**Migrate the Categories in this Data version** or **Reuse existing Odoo
Categories**. Technical model names such as `product.category`, `uom.uom`, and
`res.company` belong under **Support details**. Discovering a supporting model
must never silently authorize Impodo to create or update that model.

### Missing parents must be found before dependent records advance

A Bill of Material Line can depend on its parent Bill of Material. A Bill of
Material can depend on a Product, and that Product can come from another
incoming table or already exist in Odoo. The data manager currently experiences
the same business problem at different times depending on the relationship
origin. An incoming parent can fail during preparation, while a target-only or
Odoo-first parent can remain unresolved until Final review.

Impodo should show **Parent ready**, **Parent missing**, **Parent ambiguous**,
or **Parent set aside** as soon as the current evidence can prove that state.
The message must name the child record type, parent record type, relationship
field, relationship origin, affected record count, and correction route. The
workflow must not allow a dependent stage to look available while a required
parent remains unresolved.

### Decimal-capacity problems must be found before Load into Odoo

The captured Odoo schema already contains the target field's `digits`
metadata. After Stage 4 produces exact prepared Decimal values, Impodo can
compare those values with the captured target capacity without contacting
Odoo. Stage 4 should report potential precision loss across all prepared
values. The shared Stage 5 comparison should then identify the exact intended
writes that would lose precision.

For example, if a prepared quantity is `1.237` and the captured Odoo field can
store only two decimal places, the data manager should see the problem before
the Load page. The correction must remain explicit: either approve a documented
rounding rule in **Match data**, or ask the Odoo owner to increase the field
precision and then refresh **Odoo data**. Impodo must never round silently or
present a unit conversion as a precision fix.

### A blocked stage must always explain the correction journey

A grey or locked stage and a generic **Cannot continue** message are not enough.
Every blocked-stage projection should answer all of these questions:

1. Why is this stage blocked?
2. Which record types, fields, and records are affected?
3. Is the cause in the source data, an incoming relationship, current Odoo
   data, an Odoo field definition, or an interrupted Impodo action?
4. Who owns the correction?
5. Which exact page and decision should the data manager open?
6. Which accepted source data and saved rules remain safe and unchanged?
7. Which check must run after the correction?

The browser should display one primary correction action. It may show
alternative business decisions, such as changing Odoo precision instead of
rounding, but it must explain the consequence of each choice.

## Design rules for every improvement

Every delivery in this plan must preserve these rules:

- Impodo may suggest a choice, but the data manager confirms business meaning.
- The data manager chooses business scope. Impodo derives the bounded technical
  dependency scope from current source and Odoo evidence.
- Automatically discovered supporting models remain read-only unless accepted
  incoming data and an explicit reviewed decision place them in the write
  scope.
- Impodo must not infer identity from a translated label, choose the first
  available Odoo record, or treat a near match as equal.
- Portable mapping and Recipe evidence use business keys and scope. Numeric
  Odoo database IDs remain protected target-bound evidence.
- Opening a page must not trigger an Odoo request. A live check starts only
  after the data manager selects an explicit read-only action.
- Odoo metadata and record requests must be grouped and bounded by model and
  distinct key. No proposal may add a request per source row or browser field.
- An early check provides authoring guidance. **Final review** remains the
  authoritative fresh target comparison, and **Load into Odoo** retains its
  exact confirmation, journal, recovery, and reconciliation boundaries.
- A changed source selection, Odoo schema, matching rule, mapping, prepared
  result, target, or credential identity makes dependent guidance stale. The
  browser must explain what changed and which check must run again.
- A warning, blocker, or set-aside decision must state the cause, affected
  record or group, source or target origin, responsible role, and correction
  route.
- A required parent must be classified as ready, missing, ambiguous, or set
  aside before its dependent records can advance. The message must distinguish
  an incoming parent from a record expected to exist in Odoo.
- Exact prepared Decimal values must be checked against captured Odoo `digits`
  metadata before the Load page. Impodo must not round, truncate, or infer a
  unit conversion.
- The normal browser path uses business labels and one clear next action.
  Technical identifiers and hashes remain under **Support details**.

### Local and shared-server ownership

The same domain and application behavior must support the local desktop and
the future shared-server compositions. A product improvement in this plan
should ship locally when it is ready; it must not wait for the server release.
It must also avoid a local-only contract that the server would later need to
undo.

- Local page reads continue to use one bounded synchronous database operation.
  A local command uses one bounded local operation and never introduces a
  process-wide DuckDB connection cache.
- A shared-server request authorizes the authenticated Organization and
  Project before it can resolve detailed evidence. The implicit local actor
  and its universal capability bypass never become server behavior.
- PostgreSQL may store only bounded issue counts, stage status, current
  pointers, job progress, operation identity, and verified receipt hashes.
  Complete mappings, findings, row identities, prepared values, approvals,
  comparison detail, and reconciliation evidence remain in DuckDB or protected
  artifacts.
- A server page must not reopen a worker-owned DuckDB database. A worker
  publishes authoritative evidence and a receipt; the application verifies
  that receipt before it advances the bounded PostgreSQL projection.
- A long-running server check or mutation uses the durable job, idempotency,
  lease, fencing, interruption, and receipt contracts. Process-local managers
  remain a local adapter choice rather than the workflow contract.
- Shared code receives identity, authorization, query, job, artifact, and
  secret ports from its composition root. It must not accumulate scattered
  deployment-mode branches.

## Proposal 1: Add one cross-stage issue register

**Delivery status:** The shared projection contract is implemented for Stage 2
supporting-data blockers, current Stage 3 identity and relationship evidence,
Stage 4/5 preparation causes, and Final-review-only blocking or ambiguous
comparison causes. Current Stage 3 counts persist across workspace navigation
with freshness checked from aggregate-only evidence. One combined all-stage
drawer remains optional future consolidation rather than a prerequisite for
the next safety slice.

**Owning stages:** All six stages.  
**User impact:** **9.5/10**.

### Process improvement

Each stage should continue to own and store its authoritative evidence. A
shared application projection should present current findings through one
common issue shape:

- severity and current state;
- business cause and affected record count;
- source, incoming-table, or target origin;
- responsible role;
- owning stage and correction route; and
- evidence revision and freshness;
- work that remains accepted and unchanged; and
- the check required after correction.

This projection must not become a second mutable issue database. When the
authoritative stage evidence changes, the application recalculates whether an
issue is current, resolved, or stale. In the server profile, PostgreSQL may
retain its bounded counts, status, current evidence pointer, and verified
receipt hash. Detailed issues remain data-plane evidence and are opened only
through an authorized bounded query.

### Interface improvement

Add a persistent **Migration issues** summary to the workspace navigation. It
should show counts such as **3 Must fix** and **2 Review**. A drawer or dedicated
page should sort root causes before dependent findings.

Every issue should expose one concrete action, such as **Open Product
identity**, **Open Unit relationship**, **Review source row**, or **Prepare data
again**. After the user returns from that action, the register should say which
check must run before the issue can be considered resolved.

A locked navigation stage should expose the same explanation rather than only
showing a disabled link. For example:

```text
Final review is locked
Why: 7 Bill of Material Lines cannot find their Parent Bill of Material
Fix in: Match data -> Bill of Material Lines -> Parent Bill of Material
Your accepted source data and saved field matches remain unchanged
Then: Check matches and prepare data again
```

### Impact justification

Today, the same migration problem can appear as a Stage 3 validation reason, a
Stage 4 quality finding, and a Stage 5 comparison blocker. A common projection
prevents the user from searching six stages and repeatedly interpreting the
same cause. The score is below 10 because this improvement coordinates existing
safety evidence rather than detecting a new class of unsafe write by itself.

### Acceptance checks

- Every current blocking issue remains visible outside a paged or filtered
  field list.
- A direct action opens the owning stage and affected decision without changing
  it.
- A stale issue cannot appear resolved merely because the user visited its
  correction page.
- Every locked stage states why it is locked, what remains saved, the owning
  correction action, and the check that follows the correction.
- A generic **Cannot continue**, **Needs attention**, or **Blocked** label is
  never the only explanation for unavailable navigation.
- The projection contains no source values, target-bound identifiers, or
  credentials unless an existing protected page already authorizes them.
- In the shared-server profile, navigation reads a verified bounded projection
  and never opens a DuckDB database that an active worker owns.
- PostgreSQL stores only counts, status, current pointers, and receipt hashes.
  It does not store complete issue messages, row identities, source values, or
  protected target evidence.

## Proposal 2: Derive supporting Odoo models from business scope

**Delivery status:** Direct required-relationship and inverse-child derivation
from the live schema, plus the Stage 2 review UI, are implemented. The
Odoo-source path also implements generic per-edge relationship decisions and
guided capture plans. Source-table pairing, optional-field intent, explicit
reuse authorization, file-source Recipe closure, and value-level proof remain
proposed.

business meaning.

- reuse existing records in the destination Odoo;
- let Odoo manage or default the relationship;

   user reviews only unresolved business decisions. Impodo then suggests
   Product Internal Reference and Category Name within Parent Category; the
   identity card explains that both still need a current-data check.
3. Stage 3 maps the complete Category path, Product Unit relationship, Bill of
   Material Line parent, and Bill of Material Product. The relationship
   simulator finds seven lines without a parent Bill of Material, one missing
   Product, and two ambiguous Category paths. Each blocker names its origin and
   opens the exact relationship rule. The source-backed precision scan also
   warns that Quantity values need more decimal places than the captured Odoo
   field can store.
4. Stage 4 prepares every row. The missing Product sets aside one Bill of
   Material and its component lines. The prepared-value pass confirms every
   affected Quantity value, including any value produced only after
   transformation or normalization. The root-cause cards show the affected
   business groups, owners, preserved work, and correction routes.
5. The data manager starts the shared Odoo comparison from Stage 4. It confirms
   which precision findings affect actual writes before the Load stage can
   unlock. One unrelated Bill of Material remains safe, while the affected
   group can be explicitly set aside with every omitted record retained in the
   workbook.
6. Final review compares the reduced result with an intent of zero new Units
   and no Product price updates. Any deviation blocks confirmation.
7. Stage 6 loads the exact approved result. The cockpit shows the dependency
   groups and does not report completion until reconciliation verifies Odoo.

This scenario must also cover one interrupted request. The browser should
return to the saved journal, assess the target, and offer only the safe current
recovery action.

At every blocked step, the acceptance test should assert that the page states
the cause, affected records, owner, correction page, preserved evidence, and
required recheck. A disabled navigation item without that explanation fails
the scenario.

## Implementation and documentation boundaries

Each implemented proposal must update the owning user and developer workflow
pages registered in [`workflow.yml`](../workflow.yml). Review the following
contracts together when their behavior changes:

- [Project lifecycle](../developer/contracts/project-lifecycle.md) and
  [evidence lifecycle](../developer/contracts/evidence-lifecycle.md) for source
  scope and cross-stage freshness.
- [Canonical staging](../developer/contracts/canonical-staging.md),
  [normalization](../developer/contracts/normalization.md), and
  [quality and quarantine](../developer/contracts/quality-and-quarantine.md)
  for complete-row and root-cause behavior.
- [Preflight](../developer/contracts/preflight.md) for shared comparison,
  intent assessment, and reviewed set-aside scope.
- [Execution and reconciliation](../developer/contracts/execution-and-reconciliation.md)
  for load confirmation, recovery, and completion.
- [Server fact ownership](../architecture/server-fact-ownership.md) for the
  boundary between PostgreSQL control projections and detailed DuckDB or
  protected evidence.

The local and shared-server compositions must inject different persistence,
identity, authorization, job, artifact, and secret adapters into the same
workflow services. A new workflow query must not read the local repository
directly from shared application code. A new long-running command must expose
an immutable request and bounded progress contract that the local adapter can
run in process and the server adapter can execute through durable jobs, leases,
fencing, and receipts.

For a shared-server delivery, Organization and Project authorization must
complete before any customer evidence opens. Every bounded PostgreSQL
projection must be rebuildable from a verified data-plane receipt. A missing
or mismatched projection requires repair; it must not repeat preparation,
comparison, or Odoo transport.

Focused verification should extend the owning domain, application, browser,
artifact, security, accessibility, and performance tests rather than relying
only on documentation examples. Each live Odoo check needs request-count tests
that prove batching by model and distinct key. Each browser change needs
authenticated keyboard, focus, narrow-screen, stale-page, delayed-response,
and interrupted-action coverage.

Capture new 1440 by 1024 screenshots with isolated fictional data only after
each decision point becomes current behavior. A proposal screenshot or static
mock-up must not replace authenticated acceptance evidence.

## Non-goals

- The remaining plan does not yet implement proposal parts that the
  reassessment table and delivery-status sections still describe as proposed.
- It does not authorize automatic approval of matching rules, defaults,
  relationship matches, set-aside groups, migration intent, or Odoo writes.
- It does not add numeric Odoo database IDs to portable mappings, Recipes,
  workbooks, or ordinary browser projections.
- It does not raise current preparation or relationship scale limits.
- It does not replace Final review with an earlier advisory check.
- It does not add a second Odoo comparison to the normal Stage 4-to-Stage 5
  journey.
- It does not make the shared-server profile current, allocate a remote server,
  move detailed migration evidence into PostgreSQL, or require local users to
  run PostgreSQL or manage Organizations.
- It does not fork local and server workflow meaning. Different compositions
  provide adapters for one application contract.
- It does not weaken the separate preflight, confirmation, journaling, or
  reconciliation boundaries in the
  [generic Odoo-to-Odoo migration plan](05-odoo-to-odoo-migration.md), even though
  those pages now appear together inside Stage 6 of the Authoring workflow.
