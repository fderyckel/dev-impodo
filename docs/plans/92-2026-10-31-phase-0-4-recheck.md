# Shared-server Phases 0 to 4 recheck

## Decision supported by this report

This report records the audit requested on 2026-10-31 before more server
implementation proceeds. The implemented local account journey and the
PostgreSQL preparation trial work with fictional data. The audit nevertheless
finds security, session-management, test-maintenance, and concurrency gaps.
They need corrective work before the implementation is treated as clean or
ready for a shared deployment.

This report supplements the
[implementation plan](07-linux-server-postgresql-duckdb-implementation.md).
It does not pass the deferred Debian or Ubuntu qualification, Internet
security acceptance, or future Project collaboration gates.

This is the original audit evidence. The
[corrective checkpoint](93-2026-10-31-phase-0-4-corrective-checkpoint.md)
records the subsequent fixes, reruns, and remaining acceptance blockers.

## Findings requiring action

### 1. Keep the bootstrap password outside the web runtime

Priority: high before shared deployment. This is a confirmed secret-isolation
gap in the local topology, rather than a demonstrated remote compromise.

The
[secret provisioner](../../deploy/local-rehearsal/provision-runtime-secrets.sh)
copies the plaintext Platform Administrator password into the runtime-secret
volume with mode `0440` and group `10001`. The
[Compose configuration](../../deploy/compose.yaml) mounts that same volume into
web, worker, and bootstrap processes. A check inside the running web process
confirmed UID `10001` can read the password file after bootstrap.

A compromise of the web process therefore exposes a privileged password in
addition to the runtime database credential. Bootstrap should receive its own
secret mount. The long-lived web and worker roles should receive only the
secrets they need. Test both initial provisioning and existing-volume
upgrades, then retire or rotate the trial bootstrap password through the
supported account lifecycle.

### 2. Refresh and review the supporting images

Priority: high before shared deployment. These are scanner findings whose
reachability still needs package-specific review.

The pinned Trivy 0.76.1 scanner was run against the actual local Impodo image
and both pinned supporting images with a freshly downloaded vulnerability
database. Counts below are package alerts: a CVE affecting several packages
is counted several times.

| Pinned Caddy 2.11.7 Alpine | 1 | 9 | 7 | 9 |

The scan commands collected all critical and high alerts and did not use

### 3. Bound expensive work on public token consumption

Priority: medium for the loopback trial; resolve before exposing the routes to
untrusted clients.

The customer
[administration service](../../src/impodo/application/identity/administration_service.py)
hashes a replacement password before the repository checks whether the token
exists or can be consumed. The
[reset route](../../src/impodo/web/composition/server_account_routes.py) tries
customer recovery first and Platform Administrator recovery second. The
[platform recovery service](../../src/impodo/application/identity/recovery_service.py)
also hashes before the database check.

A bounded probe submitted one correctly shaped but never-issued token six
times. Every response was the expected generic HTTP 400, but the requests
performed twelve scrypt hashes and twelve PostgreSQL transactions. Hashing
alone consumed approximately 479 ms across these sequential requests. The
same code path has no token-consumption throttle or dedicated hashing
admission bound. Activation has the same hash-before-lookup pattern.
Container inspection also showed no configured memory or PID ceiling for
web. The trial proxy has no explicit request-body limit. These observations
are additional availability-hardening work, rather than measured exhaustion.

Add a bounded admission policy and resolve token purpose and principal kind
without hashing twice. Preserve generic rejection, single-use consumption,
expiry and security-revision checks, and short transactions. A preliminary
lookup must never replace atomic validation at consumption. Keep password
hashing outside database locks. No resource-exhaustion test was attempted.

### 4. Repair revocation of the administrator's current session

Priority: medium. This is a reproduced functional defect.

The sessions page presents a revoke form for the Organization Administrator's
own current session. The
[customer route](../../src/impodo/web/composition/server_customer_routes.py)
resolves that session before submitting the displayed revision. Session
resolution in the
[session repository](../../src/impodo/adapters/postgresql/platform_sessions.py)
touches the row and increments its revision. The displayed revision is
therefore stale by the time the revoke predicate runs.

The probe loaded the page and submitted the current session's form without an
intervening user action. It received HTTP 404, and the session still opened
`/account`. Existing lifecycle tests revoke another user's session and do not
cover this case. Either provide a deliberate sign-out action for the current
session or implement safe self-revocation using the resolved session state.
Keep cross-Organization hiding and stale-revision protection for other
sessions.

### 5. Restore behavioral contracts and their test fixtures

Priority: medium. Passing static checks do not make these failures acceptable.

The focused Phase 0 to 4 portable run reported 222 passing tests, 93 passing
subtests, and one failure. In
[the application graph test](../../tests/application/test_application_graph_composition.py),
the authoring namespace lacks `business_intents`, which the current context
builder requires. The real local builder supplies that service; the observed
failure is in the test fixture.

The default performance run reported 58 passes, nine skips, 24 passing
subtests, and five failure entries. Four are failing shapes of
`test_current_execution_call_baseline_is_explicit`; the fifth is
`test_repeated_runs_require_identical_semantic_evidence`. The
[dependency benchmark](../../scripts/benchmark_dependency_execution.py)
supplies a preflight namespace without
`current_business_intent_assessment`, which execution now calls. This blocks
measurement; it is not evidence of a measured throughput regression.

Repair the fixtures to represent accepted business-intent behavior, then
rerun the original semantic and call-count assertions. Do not add a permissive
mock that bypasses the new assessment contract or merely weaken assertions.

The older PLW scenario integration test also creates artifacts below the
repository's ignored `.tmp` directory. Move these artifacts to an operating
system temporary directory when updating the fixture, as required by the
current repository instructions.

The complete portable run subsequently exposed more failures. After a rerun
with loopback networking allowed, fifteen tests and two field-policy subcases
still failed. They include a missing derived-reference finding, changed
identity-binding expectations, a hierarchy fixture without explicit business
expectations, missing request-identity ports, and outdated version or copy
assertions. The exact inventory is below. These failures remain blocking;
neither their age nor another workstream's ownership makes them acceptable.

One legacy-storage fixture rewinds the current registry's version number to
`5` while leaving newer columns in place. Upgrade then attempts to add
`company_binding_hash` again and fails closed. Build a genuine historical
schema fixture before deciding whether production migration code needs a
change. Making every migration permissive would weaken compatibility checks.

The last complete-gate attempt found two new Basedpyright errors in
[matching-expectations parsing](../../src/impodo/web/matching_expectations.py),
which was being added by the concurrent workstream. At the observed lines 96
and 105, a `tuple[str, ...]` is passed where
`tuple[BusinessRelationshipOperation, ...]` is required, and `str` is passed
where `BusinessWriteMode` is required. These type contracts must be corrected;
the earlier zero-diagnostic result is historical evidence only.

### 6. Run behavioral contracts in continuous integration

Priority: medium.

The complete repository gate runs static quality, architecture tests, and
documentation checks. It does not run the full portable behavior suite. The
Linux workflow adds all live Linux-owned tests, but its portable integration
step enumerates only selected earlier server modules. The portable identity
domain and application suites, account route contracts, and the two broken
fixtures above are not covered by those workflow commands.

Register the intended portable behavior lane explicitly, including Phase 4
contracts. Keep live PostgreSQL tests in the Linux-owned lane. Add path
triggers for any portable test files assigned to the Linux workflow, so a
test-only change can execute its owning checks.

The final repository gate also found a newly introduced workflow-ownership
failure while concurrent work was adding matching-expectations routes:

```text
docs/workflow.yml: router must have one owner: src/impodo/web/routers/matching_expectations.py -> ()
```

The subsequent standalone documentation check also found an unowned
`src/impodo/web/routers/matching_company_refresh.py` added during the same
concurrent work. Both observed ownership failures remain blocking.

The failing test is
`DocumentationQualityTests.test_repository_documentation_has_no_objective_drift`.
The route needs its correct workflow owner and the owning documentation and
behavioral checks. This audit preserved the concurrent edit rather than
claiming that the earlier passing gate still certified the tree.

### 7. Measure and narrow Organization-wide session locking

Priority: medium for performance qualification. The locks currently help
serialize security-state changes and must not be removed without preserving
that behavior.

The customer and administrator subject queries in the session repository use
`FOR UPDATE` on the Organization row as well as the user row. Consequently,
otherwise independent users in the same Organization contend on one row
during normal session access.

A two-connection probe held the exact subject query for one fictional user
and attempted it for a different user in the same Organization. The second
query reached its configured 250 ms probe lock timeout. This establishes
contention, rather than a production throughput limit.

Before introducing a pool, measure concurrent dashboard requests and lock
waits. Investigate narrower compatible locking while retaining immediate
suspension and administrator-replacement semantics, consistent lock order,
and bounded transaction lifetimes. Short-lived connections remain the
appropriate default until there is evidence that a pool helps.

### 8. Reject malformed anonymous CSRF cookies safely

Priority: low. This is an input-handling defect, with no demonstrated access
bypass or secret disclosure.

The public account form checks that the submitted token is ASCII, but does
not apply the same check to the anonymous cookie before calling
`hmac.compare_digest`. A single loopback request with a non-ASCII cookie and
an ASCII form token returned HTTP 500 instead of a bounded rejection. The
response did not contain the fictional submitted password.

Validate both inputs before comparing them and add a malformed-cookie
regression case. Keep the existing CSRF, exact-origin, and cookie policy.
