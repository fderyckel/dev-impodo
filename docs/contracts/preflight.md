# Profile-driven preflight contract

## Status and scope

**Status:** Implemented for both strict CLI profiles and submitted browser
mapping revisions.

The preflight engine answers, without changing Odoo:

> For these source rows and exact target snapshots, which records would be
> created or updated, which are unchanged, and which cannot be decided safely?

Its outputs are review evidence, not an executable import plan or Odoo write
authorization.

```text
strict profile or submitted browser mapping + frozen CSV/XLSX
-> typed prepared records
-> batched target requirements
-> metadata and record snapshots
-> resolve, match, compare, classify
-> portable manifest and workbook projection
```

## Profile invariants

A strict YAML profile declares datasets, contained CSV files or explicit XLSX
worksheets, target models, modes, identities, scopes, scalar mappings,
relations, and optional target domains. Unknown keys, duplicate datasets,
invalid relation origins, inconsistent key arity, and dependency cycles fail
before processing.

Dataset modes are:

- `upsert`: create when missing and compare one match;
- `create`: create when missing and apply an explicit existing-record policy;
- `reference`: support relationship resolution without producing an import
  decision.

Profiles contain no target URL, database, credential, token, or numeric Odoo
record ID. Detailed YAML examples belong in the
[profile authoring guide](../operations/profile-authoring.md).

## Prepared-record boundary

Every nonblank input row produces an immutable `PreparedRecord`, including
rows with validation issues. It keeps these concepts separate:

- source row and source trace identity;
- target model, ordered identity, and business scope;
- typed scalar values;
- symbolic incoming or existing-target references;
- structured issues.

Supported portable values are string, arbitrary-precision integer, `Decimal`,
boolean, date, timezone-aware UTC datetime, null, and business-key references.
Decimals never pass through binary floating point.

Incoming relationships remain symbolic until dependency resolution. Existing
target relationships are converted to model, ordered business key, and scope.
Prepared records never contain numeric Odoo IDs.

Parsing continues far enough to preserve row traceability. Error-severity
source, type, identity, duplicate, or relationship issues make the record
blocking rather than silently dropping it.

## Odoo read boundary

The preflight port exposes only:

```python
get_target_fingerprint()
get_model_metadata(requests)
get_records(requests)
```

The live Odoo 19 JSON-2 adapter allowlists only `fields_get` and
`search_read`. There is no create, write, unlink, import, generic method, SQL,
server action, or mutation-capable context surface.

Requests contain exact models, projected fields, and bounded domains produced
by the planner. Metadata and record requirements are merged per model; target
reads use deterministic `id asc` pagination. No connector call may occur
inside a source-row loop. Large future `in` domains must be split into bounded
transport requests rather than one request per row.

## Target fingerprint and snapshots

Metadata and record snapshots share one target fingerprint. Its hash binds
connection mode, normalized base URL, and database; the portable evidence
also records database, Odoo version, capture time, and relevant module
versions without exposing the URL or credentials.

Metadata snapshots contain only requested model/field attributes. Record
snapshots contain exact requested fields and captured Odoo records. Numeric
Odoo IDs are permitted only in target-specific record snapshots and internal
indexes so relationships can be reverse-resolved to business keys.

Saved evidence must satisfy:

- matching metadata/record fingerprints;
- `complete: true` before classification;
- profile and source bindings when present;
- exact file-byte SHA-256 hashes recorded in the manifest;
- canonical JSON and atomic replacement when written.

Current snapshot loading does not require every envelope binding, persist the
planned domain/requirements hash, or apply a complete JSON Schema. Saved live
evidence should therefore be generated by the CLI and retained unchanged.

## Resolution and classification

Source identities detect duplicate input rows. Target identity plus scope
forms the target lookup key. Target duplicates remain visible.

Incoming references resolve against another prepared dataset. Existing-target
references resolve through preloaded business-key indexes. Missing, ambiguous,
or blocked dependencies create structured evidence according to the declared
policy.

Every import candidate receives exactly one result in fixed precedence:

| Priority | Condition | Result |
| ---: | --- | --- |
| 1 | Blocking source, metadata, identity, reference, or comparison issue | `BLOCKED` |
| 2 | Multiple complete scoped target matches | `AMBIGUOUS` |
| 3 | No target match and create requirements satisfied | `CREATE` |
| 4 | One match with material differences | `UPDATE` |
| 5 | One match without material differences | `UNCHANGED` |

Scalar comparison applies the same declared type, normalization, precision,
and null policy to source and target values. Many2one and many2many values are
compared through portable business references; many2many supports explicit
`replace`, `add`, and `remove` semantics.

## Portable result

`impodo_preflight_manifest.json` contains source and snapshot hashes, profile
ID, target fingerprint, classification totals, decisions, exact field
differences, grouped relationship evidence, issues, metadata coverage, and a
semantic hash over the payload.

Every decision retains dataset, source row, business identity/scope, match
count, classification, differences, and issues. The serializer rejects
`odoo_id`, `odoo_ids`, `record_id`, and `record_ids` recursively, together with
credentials and transport authorization data.

`impodo_preflight_report.xlsx` is a projection of the manifest. It contains no
independent matching or classification logic; workbook failure does not turn
an incomplete review package into a valid one.

Canonical ordering, typed portable values, and stable JSON encoding make the
manifest byte-deterministic for unchanged saved inputs. The semantic hash
currently binds the profile by ID rather than profile-file hash and does not
include a persisted requirements-plan hash.

## Integration boundary

The browser compiles the exact submitted mapping into the same preflight
contract, stages every frozen source row, and repeats related parent/child
generation over the complete dataset. Summary presents `CREATE`, `UPDATE`,
and `UNCHANGED` as **Ready**, `AMBIGUOUS` as **Needs review**, and `BLOCKED` as
**Blocked**, with dataset and source-row evidence.

Mapping submission, preflight classification, clean-package certification,
functional approval, and Odoo execution remain separate states. The browser
readiness check is read-only and grants no Odoo write capability.
